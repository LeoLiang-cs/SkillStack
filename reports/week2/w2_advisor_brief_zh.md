# SkillStack Phase 2A——第二次导师简报（中文版）

- **当前状态：** Phase 2A（技能条件化执行）已完成，H1 gate 通过。
- **实验环境：** ALFWorld 文本环境，`valid_unseen`，5 个固定任务。
- **本阶段回答的问题：** 选中的技能是否真的改变 agent 的行为与任务结果？——可以，且可测量。

## 1. 与上次汇报相比，发生了什么变化

上次的 P0.0 只能证明**结构可替换**：两种配置都只回放一个固定的 `look` 动作，任务成功率不可测量，技能选择没有任何下游后果。

Phase 2A 把固定动作回放执行器替换为**确定性多步执行器**（`SkillPlanExecutor`，手写策略，无 LLM）：它从所选技能的 `Procedure` 推导计划骨架，并为每个动作记录 `action_rationale`（动作↔技能步骤对应）。四种技能输入条件共享同一执行器：

| 条件 | 检索器 | 角色 |
|---|---|---|
| C-no-skill | `NoSkillRetriever` | 下界 |
| C-random | `RandomSkillRetriever`（按任务固定种子） | 错误技能对照 |
| C-lexical | `DebugLexicalRetriever` Top-2 | 现有检索器 |
| C-oracle | `OracleSkillRetriever`（冻结映射） | 上界 |

四个条件共享 6 个原生技能、同一适配器、5 个冻结任务、seed 42、步数预算 50 和 JSONL 轨迹格式。

## 2. 结果

| 条件 | 任务成功 | 样本数 | 停止原因分布 |
|---|---:|---:|---|
| C-no-skill | **1/5** | 5 | env-done 1；计划完成 3；步骤不可用 1 |
| C-random | **1/5** | 5 | env-done 1；步骤不可用 2；步骤预算耗尽 2 |
| C-lexical | **3/5** | 5 | env-done 3；计划完成 2 |
| C-oracle | **5/5** | 5 | env-done 5 |

逐任务：

| 任务族 | no-skill | random | lexical | oracle |
|---|---|---|---|---|
| 灯光检查 | ✗（无灯步骤） | ✗（拿到 heat 技能） | ✓ | ✓ |
| 简单取放 | ✓ | ✓（随机撞对） | ✗（Top-1 是灯光技能） | ✓ |
| 清洗后放置 | ✗（无清洗步骤） | ✗（拿到 heat 技能） | ✓ | ✓ |
| 加热后放置 | ✗（无加热步骤） | ✗（拿到灯光技能） | ✗（Top-1 是冷却技能） | ✓ |
| 冷却后放置 | ✗（无冷却步骤） | ✗（拿到灯光技能） | ✓ | ✓ |

## 3. H1 gate

> C-oracle 必须严格优于 C-no-skill 与 C-random。

结果：oracle 5/5，no-skill 1/5，random 1/5——**通过**。在当前执行器下，技能通道对任务结果有因果效应，检索指标从此有了可测量的下游目标。

## 4. 最有信息量的发现

上次的两个检索错配现在有了**可测量的下游失败**：

- **加热任务**（"Put the cooked green apple in the fridge"）：lexical Top-1 选了冷却技能；执行器把苹果冷却后放进冰箱、计划正常结束——但目标要求苹果是*热*的。任务失败（15 步）。
- **取放任务**（"Move a mug from the shelves to the desk"）：lexical Top-1 选了灯光技能（上次的并列问题）；执行器拿起马克杯后去找灯并打开灯——杯子从未被移动。任务失败（7 步）。

由于适配器在这 20 个 episode 中仍然记录零丢弃/零近似/零默认，失败可以归因于**检索语义**而非数据转换——上一版简报留下的归因缺口（F-05）被补上了。

## 5. 新的摩擦发现

摩擦向下游移动了一个边界：适配器仍然无损，但**执行器硬编码了关于 6 个具体技能 id 的知识**（计划骨架、家电名称）。一个真正的新技能会被忽略或错误执行。这是目前最强的接口归纳证据：procedure 结构与 `required_transformation` / `required_appliance` 字段。完整台账见 [`w2_friction_ledger.md`](w2_friction_ledger.md)。

## 6. 现在可以主张的结论

1. 任务成功率第一次可测量，且技能选择在确定性执行器下因果地改变成功率（oracle 5/5 vs no-skill/random 1/5）。
2. 上次的两个检索错配都产生了可测量的任务失败。
3. 20 个 episode 中适配器始终无损；耦合在执行器一侧（技能 id 特定的计划骨架），不在适配器一侧。
4. no-skill 基线行为可解释：它只能完成"计划恰好等于通用取放骨架"的任务。

## 7. 仍然不能主张的结论

1. 任何关于 LLM agent 的结论：执行器是手写的。
2. 统计显著性或泛化性：只有 5 个任务，只报原始计数。
3. `goal_operation` / `required_transformation` 一定是*接口*字段：它们可能只是检索器内部特征（Phase 2B 会检验）。
4. Canonical Interface v1；acquisition/governance；图组合。

## 8. 建议的下一步：Phase 2B

因果链已闭合，检索语义可以用可测量的目标来研究。固定执行器、任务、技能库、种子与预算，只替换检索器：

1. R1：词法 + 词形/同义词归一化（检验加热失败是否只是 `cooked`↔`heat` 的覆盖问题）。
2. R2：显式提取 `goal_operation` 与 `required_transformation` 的任务语义检索器（检验这些是否是缺失的语义）。
3. R3：读取原始 observation 的 state-aware 检索器（检验状态适用性，对应第一版台账 F-03）。
4. 在得出分布性结论之前，扩充每任务族实例并加入语义保持改写。

执行器一侧的耦合发现（F-06/F-07）提示应并行回答：**第三个真正的新技能**要被正确消费需要什么——这是 Canonical Interface v1 的第一份具体输入。

## 9. 希望与导师讨论的决策

1. 是否认可在固定执行器上推进 Phase 2B 检索干预？
2. LLM ReAct 执行器（执行器槽位的替换目标）的模型访问：用哪个 backbone、什么预算？这仍是唯一硬 blocker。
3. 任务规模：在决定接口字段之前，每个任务族需要多少个实例、多少改写？

## 10. 四页汇报结构

1. **问题**：选中的技能是否改变行为与结果？
2. **设计**：确定性执行器 + 4 条件 + 动作理由记录。
3. **证据**：H1 表格；加热任务现在可测量地失败；摩擦从适配器移到执行器。
4. **决策**：Phase 2B 检索替换；LLM 执行器替换需要模型访问。

## 11. 口头汇报稿

"上次的流水线结构上可替换，但技能不影响任何结果，因为执行器只回放一个 `look`。这一周我做了一个真正读取所选技能的确定性多步执行器，用四种输入跑它：无技能、随机技能、词法检索和 Oracle。

Oracle 完成全部五个任务，无技能和随机各完成一个。技能通道现在可测量地改变结果，第一版简报留下的因果缺口闭合了。之前看到的两个检索错误——加热任务检索到冷却技能、取放任务检索到灯光技能——现在都产生了可测量的任务失败，而适配器仍然零信息丢失，所以问题在检索语义，不在数据转换。

新的摩擦在下一层边界：执行器为我们的六个具体技能硬编码了计划骨架，一个真正的新技能不会被正确消费。这是到目前为止关于'共享接口应该包含什么'的最强证据。下一步我建议固定执行器，只换检索器——同义词归一化、显式任务语义、状态感知打分——来检验那两个失败到底来自词法覆盖还是接口缺失。LLM 执行器的模型访问还需要一个决定。"
