# SkillStack Phase 2C——第三次导师简报（中文版）

- **当前状态：** 执行器槽位替换完成；DeepSeek pilot 已分析；GLM pilot 作为可移植性对照记录中。
- **一句话结论：** 替换本身成功，但暴露出"5 个冻结任务对 deepseek-v4-flash 零样本太简单"——技能注入无可测收益。两个发现都如实报告。

## 1. 与上次汇报相比，发生了什么

第二周的确定性 `SkillPlanExecutor` 被替换为**零样本 ReAct 执行器**（外部 LLM 驱动），runner、适配器、检索器、冻结任务和轨迹格式**零改动**——这是第一次真正的执行器槽位替换（RQ2 边界测试）。

- `src/skillstack/llm/client.py`：零依赖 OpenAI 兼容客户端，重试、每次调用的 usage/延迟/成本核算，禁用原生思考模式。
- `src/skillstack/execution/react.py`：严格 Thought/Action 循环，逐字校验 admissible 命令，非法重试 1 次（反馈中重列命令表），逐步 rationale 与 token 核算。
- 后端：`glm-4.7-flashx`（z.ai）为主、`deepseek-v4-flash` 为备，配置在 `configs/llm_backends.json`；密钥走 git-ignored 的 `.env`。

全量前做了 5 任务双后端 oracle 探针，形成计划附录（`plan_phase2c.md` 第 8 节）：严格 ReAct 的命令合法性由 DeepSeek 满足（0 非法动作）、GLM 不满足（非法动作频发）。因此全量四条件以 DeepSeek 为主证据，GLM 保留为**记录在案的可移植性运行**。

## 2. 结果（deepseek-v4-flash，50 步预算）

| 条件 | 成功率 | 平均步数 | LLM 调用数 | 估算成本 |
|---|---:|---:|---:|---:|
| no_skill | **5/5** | 14.2 | 71 | $0.016 |
| random_skill | **5/5** | 20.0 | 100 | $0.025 |
| lexical | **5/5** | 21.2 | 106 | $0.028 |
| oracle | **4/5** | 26.3（成功集） | 115 | $0.025 |

- 20 个 episode **0 次非法动作**（格式合法率 100%）。
- 唯一失败是 oracle 条件的灯光任务：模型在第 8 步过早宣布 `done`，未同时满足两个目标条件。
- 逐任务成功率全部触顶；差异只在**效率**上，而最省步数的反而是 no-skill 条件。

## 3. Gates 结果

- **G1（格式）：** DeepSeek 通过（0 非法）；GLM 失败（非法动作致死，见 F-15）。
- **G2（技能通道）：** **失败**。C-oracle（4/5）未严格优于 C-no-skill（5/5）/C-random（5/5），且技能注入没有降低步数。计划已预告此情形：当 backbone 在预算内零样本解题时，技能上下文没有被有意义地消费。
- **G3（替换）：** 通过。runner/适配器/检索器/轨迹零改动；所有轨迹同形且新增 LLM 核算字段。

## 4. 诚实解读

1. **执行器槽位在结构上可替换**——prompt 策略替换手写策略，未触碰相邻组件。
2. **测量区间饱和**：5 个单家族任务 × 50 步对 `deepseek-v4-flash` 太简单。技能效用无法在"无技能也能触顶"的区间里测量。这是任务集+预算的负结果，不是技能思路的负结果。
3. **后端可移植性是有条件的**：同一严格执行器在 DeepSeek 上工作、在 GLM 上命令合法性失败。这是项目第一例"组件不能无损跨后端移植"（F-15）。
4. **temperature=0 跨厂商不可复现**（F-21）：相同条件在探针与 pilot 之间产生了不同轨迹。

## 5. 摩擦台账新增

F-15…F-21 见 [`w3_friction_ledger.md`](w3_friction_ledger.md)：嵌套容器物件的命令词汇、原生思考吞噬输出预算、环境步数上限语义、平文本技能消费 vs 结构化计划、prompt 版本效应、价格波动、采样非确定性。

## 6. 现在可以主张的结论

1. 执行器槽位在结构层面可互换，轨迹含完整 token/成本/延迟核算（35/35 单测；20+ 已记录 episode）。
2. 在该任务集与预算下，`deepseek-v4-flash` 零样本 ReAct 使成功率触顶，平文本技能上下文无可测收益——项目的第一个天花板发现。
3. 严格执行器不能无损跨后端移植（GLM 合法性失败）；prompt 迭代有帮助但未治愈。

## 7. 仍然不能主张的结论

1. 任何关于"技能效用"的一般性结论——天花板掩盖了它。
2. GLM 级模型配上更好 prompt（如 few-shot）做不了 ReAct——该变体尚未测试。
3. 统计结论（5 任务，只报原始计数）。

## 8. 建议的下一步

固定执行器，改变**测量区间**，按序：

1. **收紧步数预算**（如 10 步）：在零样本 ReAct 吃力的区间里，oracle 技能上下文能否救回 no-skill 救不回的 episode？把效率压力转化为成功率差异。
2. **加入更难的任务**：manifest 刻意排除的 `pick_two_obj_and_place` 家族 + 每家族第二实例。
3. 之后才测试**结构化技能注入**（procedure 步骤而非平文本）——把第二周 F-06/F-07 的候选具体化。

## 9. 希望与导师讨论的决策

1. 下一周采用紧预算区间（如 10 步），还是保持 50 步并把天花板作为负结果发表？
2. GLM 后端：保留为记录在案的可移植性失败，还是加 few-shot prompt 变体尝试补救？
3. 现在就扩任务集（pick_two + 更多实例），还是等区间问题定下来再扩？

## 10. 四页汇报结构

1. **替换**：prompt 版 ReAct 替换手写执行器，零相邻改动，完整核算。
2. **证据**：5/5/5/4 成功率表；0 非法动作；步数统计。
3. **发现**：天花板效应（G2 失败）、GLM 合法性可移植性失败、temp-0 非确定性。
4. **决策**：紧预算 / 扩任务 / 结构化技能——下一区间选哪个？

## 11. 口头汇报稿

"上周确定性执行器证明了技能改变结果——但那是因为技能本身就是计划来源。这一周我把执行器换成了真正的 LLM ReAct，其他组件一个没动：替换本身成功，轨迹里有完整的 token 和成本核算。

结果是一个教科书式的天花板效应：DeepSeek 零样本就能解完五个冻结任务，连无技能条件都 5/5，而且 no-skill 反而是最省步数的。唯一失败是 oracle 条件的灯光任务——模型过早宣布完成。所以在这个区间里，技能通道没有可测收益，我承诺的 gate 按计划预告的方式失败了。

第二个发现是可移植性：同一个严格执行器在 GLM 上反复提出不可执行的命令。这是我们第一例'组件不能无损跨后端移植'的记录。

下周我建议：执行器不动，把步数预算收紧，让零样本 ReAct 不再触顶——这样就能看到技能上下文能不能救回无技能条件救不回的 episode；另外把 manifest 刻意排除的双物体任务加进来。"
